# Codex GUI 上下文容量隔离验证

2026-09-15，Windows 11 Hyper-V 虚拟机 `win11`（设备名 `ZH2`），Codex CLI 0.154.0。
虚拟机沿用现有 Codex Remote Provider，连接上游 Codex Remote，使用真实模型 `gpt-6-astra`。

GUI 对话保存的容量原本会被模型列表中的账户或 Provider 上限压低。
代理会话列表也从账户或 Provider 配置推算容量，无法反映 GUI 对话的实际设置。

修复后，GUI 模型列表允许对话容量覆盖，账户页的官方模型限制只用于账户页对应的请求。
GUI 的代理会话保存 CLI 实际回报的可用容量；保存、重启后的历史读取均保留该值。
背景信息弹窗重新打开时读取当前对话设置，避免弹窗缓存旧值，并分别展示已保存设置和最近回复的可用容量。

## 虚拟机实测

新建独立测试对话，所有消息均要求不调用工具、不修改文件。
账户页始终保持 272K，普通 Provider 会话仍显示其原有容量。

| GUI 对话设置 | 真实回复的可用容量 | 背景信息弹窗 | 代理会话列表 |
| --- | --- | --- | --- |
| 默认 | 258.4K | 258.4K | 258.4K |
| 300K | 285K | 285K，同时显示设置 300K | 285K |
| 1000K | 828.4K | 828.4K，同时显示设置 1M | 828.4K |
| 400K | 380K | 380K，同时显示设置 400K | 380K |

可用容量以 CLI 实际回报为准，仍受模型自身上限和预留空间影响。
重新打开设置时，输入框正确恢复之前保存的 300K。

在真实请求进行中打开代理会话窗口，观察到活动请求数从 1 回到 0、容量更新为 285K。
三次会话刷新分别约 12.8、14.5、8.4 毫秒；约六秒内记录到 193 次页面动画帧回调。
手机连接状态在测试过程中保持已连接。

## 运行中修改容量

保存当前对话的容量时，GUI 先暂停正在执行的轮次，等待完成事件，再重新加载该对话并应用容量。
保存成功后，在原对话中发送“请继续完成刚才中断的任务。”继续工作；不会重新发送原始请求或附件。
空闲对话直接应用，不额外发送消息。其他对话继续执行，共享的 Codex 进程保持连接。

保存与发送按对话串行处理；暂停失败时不修改容量，保存失败时尝试恢复原容量并保持暂停。
恢复失败时显示“容量已更新，但未能继续回复”，允许用户关闭设置后手动继续。
这不是恢复被中断工具的执行现场；模型会依据已有历史继续处理任务。

使用已安装的 Codex CLI 0.154.0 和本地 Responses 测试服务验证（不调用真实模型）：

```powershell
node scripts/codex-gui-context-pause-smoke.mjs <codex.exe路径>
```

- 工具调用期间暂停，384K 设置在继续后的用量事件中回报 364.8K。
- 同一对话保留中断前的历史，恢复默认后回报测试配置原有的 190K。
- 另一对话的 HTTP 请求在容量切换期间继续保持活动，其容量仍为 190K。
- 任务执行期间连续读取对话状态成功；设置弹窗测试覆盖刷新未完成时的交互、保存等待和恢复失败。
